## Cache Coherence

### The Problem

![[Pasted image 20260503120106.png]]

In a shared memory multiprocessor, each processor has its own local cache. When multiple processors maintain locally cached copies of a unique shared-memory location, any local modification of that location can result in a globally inconsistent view of memory. Cache coherence schemes prevent this problem by maintaining a uniform state for each cached block of data.

To understand the inconsistency, consider two processors P1 and P2 both caching a block X from shared memory. Before any update, all three copies — P1's cache, P2's cache, and shared memory — hold the value X. Now P1 writes X' to its cache:

- In a **write-through** cache: P1's cache and shared memory are updated to X', but P2's cache still holds the stale value X.
- In a **write-back** cache: only P1's cache is updated to X'. Shared memory and P2's cache are both stale.

In both cases, P2 is reading incorrect data. This is the cache coherence problem.

---

### Snoopy Protocols

![[Pasted image 20260503120130.png]]


Snoopy protocols achieve data consistency among caches and shared memory through a **bus-watching mechanism**. Every cache controller monitors (snoops) all bus transactions. Since all caches see every bus transaction, each controller can update its own state accordingly — either invalidating or updating its local copy.

Snoopy protocols come in two flavors:

- **Write-invalidate protocol**: when processor P1 writes to a block, all other cached copies of that block are **invalidated** (marked as invalid). Other caches must fetch the new value on their next access.
- **Write-update protocol**: when P1 writes, the new value is **broadcast to all other caches** that hold a copy, updating them simultaneously.

After a write-invalidate operation by P1: P1's cache holds X', all other caches hold I (invalid), shared memory may or may not be updated depending on write-back or write-through policy.

After a write-update operation by P1: P1's cache and all other caches hold X', shared memory holds X'.

> **PYQ (CT-II 2021 Q1):** If a processor writes into a block in its local cache, all other caches also obtain the new content immediately in the **(b) write-update protocol**. In write-invalidate, other caches are invalidated, not updated.

### MSI Write-Back Invalidation Protocol

The MSI protocol is a snoopy, write-back, write-invalidate protocol. Each cache block can be in one of **three states**:

**Modified (M)** — also called "dirty". Only this cache has a valid copy of the block. The copy in main memory is stale. This cache has exclusive ownership and is responsible for supplying the data if another cache requests it.

**Shared (S)** — the block is present in an unmodified state in this cache. Main memory is up-to-date. Zero or more other caches may also have an up-to-date (shared) copy.

**Invalid (I)** — the block is not present in this cache, or the copy present is stale and cannot be used.

#### Bus Transactions

The bus allows three types of transactions in MSI:

**BusRd (Bus Read)** — generated by a cache controller when a processor read (PrRd) misses in the cache. The controller puts the address on the bus and requests a copy that it does not intend to modify. The memory system (or possibly another cache) supplies the data.

**BusRdX (Bus Read Exclusive)** — generated by a cache controller when a processor write (PrWr) targets a block that is either not in the cache, or is in the cache but not in the Modified state. The controller puts the address on the bus and requests an exclusive copy that it intends to modify. The memory system (or possibly another cache) supplies the data. All other caches are invalidated.

**BusWB (Bus Write Back)** — generated by a cache controller on a write-back. The processor does not know about it and does not expect a response. The controller puts the address and the contents of the memory block on the bus. Main memory is updated with the latest contents.

> **PYQ (2022 Q17):** A BusWB transaction **(a) is generated by a cache controller**. It is not generated by the processor. It does not involve the processor knowing anything — the cache controller initiates it autonomously.

#### Notation for State Transition Diagrams

Transitions are written as **Event / Action**. If the controller observes event A (from the processor side or the bus side), it performs action B in addition to the state change. A dash "—" means null action (nothing is generated on the bus).

- Transitions due to **observed bus transactions** are shown in dashed arcs.
- Transitions due to **local processor actions** are shown in bold arcs.

Replacements and the write-backs they may cause are not shown in the diagram.

|---|---|---|---|

**Reading the table:** "Event" is either a processor-side request (PrRd, PrWr) or an observed bus transaction (BusRd, BusRdX). "Action" is what this cache controller puts on the bus in response, or "—" if nothing.

#### Detailed Explanation of Key Transitions

**I → S on PrRd:** A processor read to an invalid (not present) block causes a BusRd transaction. The newly loaded block is promoted to the Shared state in the requesting cache, whether or not any other cache holds a copy. Any other cache with the block in the Shared state observes the BusRd but takes no special action — it allows main memory to respond. However, if a cache has the block in the **Modified state** (there can only be one such cache), it must get involved since main memory is stale. That cache flushes the data onto the bus in lieu of memory, and demotes its own copy to the Shared state. Both the memory and the requesting cache pick up the block. This can be accomplished either by a direct cache-to-cache transfer across the bus during the BusRd transaction, or by signalling an error on the BusRd and generating a write transaction to update memory, after which the original cache retries and obtains the block from memory.

**I → M on PrWr (write miss):** Writing into an invalid block is a write miss. It is serviced by first loading the entire block and then modifying the desired bytes within it. The write miss generates a BusRdX transaction, which causes all other cached copies of the block to be invalidated, thereby granting the requesting cache exclusive ownership. The block returned by the read exclusive is promoted to the Modified state, and the desired bytes are then written into it. If another cache requests exclusive access later via BusRdX, this block will be invalidated (demoted to the Invalid state) after flushing the exclusive copy to the bus.

**S → I on BusRdX:** If this cache observes a BusRdX from another cache, it means that other processor intends to write the block. This cache must invalidate its copy immediately.

**M → S on BusRd:** If this cache (the only one with a valid, modified copy) observes a BusRd from another cache, it must flush the data onto the bus — it cannot allow memory (which has a stale copy) to respond. After flushing, it demotes its copy to Shared.

**M → I on BusRdX:** If another cache issues a BusRdX targeting this block, this cache flushes the data onto the bus and moves to Invalid.

> **PYQ (2023 Q4):** In the MSI protocol, if a cache controller observes a BusRdX while its cache is in the M-state, it changes its state to **(a) I** — and it flushes its data first.

> **PYQ (2022 Q25):** In the MSI protocol, if a bus is in the M state and observes a BusRd transaction, it **(c) flushes its data onto the bus and changes to the S state.**

> **PYQ (2022 Q23, 2022 Q24):** In the MSI protocol, if a cache is in the S state and receives a PrRd, the state **(c) remains S unchanged.** If it observes a BusRdX, it changes to **(a) I.**

> **PYQ (2019 Q8):** If a cache in state M observes a BusRdX transaction, it **(d) flushes its contents and moves to state I.**

> **PYQ (2019 Q10):** If a cache in state M observes a BusRd transaction, it **(a) moves to state S** (after flushing).

> **PYQ (2018 Q8, Q9, Q10):** These questions trace state transitions through a sequence of events E1, E2, E3. Apply the transition table above row by row — start in I, apply each event, track the state and whether main memory or another cache has the valid copy.

### MSI Drawback — Motivation for MESI

In MSI, when a process reads in and then modifies a data item, two bus transactions are generated: (i) a BusRd that gets the memory block into the S state, and (ii) a BusRdX (or BusUpgr) that converts the block from S to M state. This second transaction takes place even if no other processor is sharing this block — it is not known whether other processors are sharing the block, so the upgrade transaction must happen regardless. This is wasteful.

---

### MESI Write-Back Invalidation Protocol

MESI solves the MSI drawback by adding a fourth state: **Exclusive (E)**, also called exclusive-clean or exclusive-unowned. The E state indicates that this cache is the only (exclusive) copy of the block, but the block has **not been modified** — main memory has a valid copy. Because no other processor is caching the block, the cache can perform a write and move directly to the Modified state **without any bus transaction**. The second bus transaction of MSI is saved.

The E state is an intermediate level of binding between Shared and Modified. Unlike the Modified state, it does not imply ownership (memory has a valid copy), so the cache need not reply upon observing a request for the block.

#### The Shared Signal (S)

MESI places a new requirement on the physical interconnect of the bus. An additional signal called the **shared signal (S)** must be available to all controllers. During the address phase of a BusRd transaction, all caches determine if they contain the requested block and, if so, **assert the shared signal**. This tells the requesting cache whether any other cache currently holds the data — if no other cache asserts S, the block can be loaded into the E state; if S is asserted, it must go into the S state.

> **PYQ (2021 Q16, 2023 Q16, 2025 Q—):** The shared signal (S) in the MESI protocol **(a) enables a cache controller to determine on a BusRd whether any other cache currently holds the data.**

#### MESI States

**Modified (M)** — same as MSI. Only this cache has a valid copy; main memory is stale.

**Exclusive (E)** — only this cache has a copy; main memory is also valid. No other cache has a copy. The cache can write without generating a bus transaction.

**Shared (S)** — this cache has a valid, unmodified copy. Main memory is valid. One or more other caches may also have a copy.

**Invalid (I)** — the block is not usably present in this cache.

|---|---|---|---|
|I|PrRd (S signal inactive)|E|BusRd|
|I|PrRd (S signal active)|S|BusRd|

|E|PrWr|M|— (no bus transaction needed!)|
|E|BusRd|S|Flush'|

|S|PrWr|M|BusRdX|

|M|BusRd|S|Flush|
|M|BusRdX|I|Flush|

**Flush'** applies to the cache that supplies the data (instead of main memory) on a BusRd or BusRdX. It applies to the cache that supplies the data, not the requesting cache.

#### Key Transitions Explained

**I → E on PrRd (S inactive):** A read miss occurs, a BusRd is placed on the bus. During the address phase, all other caches check whether they hold this block. None assert the S signal. The block is loaded from memory into the Exclusive state — this cache is the only copy.

**I → S on PrRd (S active):** Same read miss, but at least one other cache asserts the S signal, meaning another cache holds the block. The block is loaded into the Shared state.

**E → M on PrWr:** The cache is the only copy and memory is valid. A write can be performed by simply updating the cache block and moving to Modified — **no bus transaction is generated**. This is the key advantage of the E state over MSI.

**E → S on BusRd:** Another cache issues a BusRd for this block. This cache was the exclusive holder, so it supplies the data (Flush') and moves to Shared. The requesting cache also loads it as Shared.

**S → M on PrWr:** A write to a Shared block requires a BusRdX to invalidate all other copies first.

> **PYQ (2018 Q31, 2019 Q31):** In MESI, if a cache in the S state observes a BusRdX, it moves to **(b) I-state.**

> **PYQ (2018 Q32, 2019 Q32):** In MESI, if a cache in the I state receives a PrRd, it moves to **(c) E-state if the shared signal is inactive**, or **(b) S-state if the shared signal is active.** The correct combined answer is **(c) both (a) and (b)** as stated in the options.

> **PYQ (2022 Q21):** On receiving a PrWr request, a cache in the S state **(a) generates a BusRdX transaction.**

> **PYQ (2022 Q22):** When a cache in M state observes a BusRd transaction, it **(d) both moves to the shared state AND flushes its data on the bus.**

> **PYQ (2022 Q23):** When a cache in I state receives PrRd, it **(d) moves to E-state if the shared signal is NOT asserted, S-state if shared signal IS asserted.**

> **PYQ (2022 Q40, 2024 Q20):** Cache-1 in E state observes a read request from Cache-2. **(b) Cache-1 need not send the block to Cache-2 since main memory has a valid copy** — because E means unmodified, memory is valid.

### Directory-Based Cache Coherence

![[Pasted image 20260503120240.png]]


Snoopy protocols rely on a shared bus — every cache sees every bus transaction. This does not scale to large multiprocessors because the bus becomes a bottleneck. **Directory-based cache coherence** is used in scalable multiprocessors. Instead of broadcasting transactions to all caches, a **directory** tracks which caches hold copies of each block, and transactions are sent only to the relevant caches using point-to-point network messages.

Each node in the system consists of a processor, a cache, local memory, a directory, and a **communication assist (CA)** — the hardware/firmware that handles network transactions on behalf of the processor.

#### The Directory Entry

A natural way to organize a directory is to maintain the directory information for a block **together with the block in main memory**, that is, at the **home node** for the block.

For each cache-line-sized block of main memory, there is a directory entry containing:

- A **presence bit vector** of PP bits (one per node/processor), where presence[i]=1presence[i]=1 means node ii currently has a cached copy of the block.
- A **dirty bit**, which indicates if the block is dirty (modified) in one of the node caches. If the dirty bit is ON, then only one node should be caching that block, and only that node's presence bit should be ON.

```
Directory entry for one block:
+-------+---+---+---+-----+---+
| Dirty | P1| P2| P3| ... | Pn|   <- presence bits
+-------+---+---+---+-----+---+
```

When the dirty bit is ON, only one presence bit is ON (the dirty/owner node). When the dirty bit is OFF, multiple presence bits may be ON (multiple clean shared copies are allowed).

#### Node Terminology

![[Pasted image 20260503120333.png]]

|Term|Meaning|
|---|---|
|**Home node**|The node in whose main memory the block is allocated. The directory entry for the block lives here. May be the same as the requestor.|
|**Dirty node**|The node that has a copy of the block in its cache in the Modified (dirty) state.|
|**Owner node**|The node that currently holds the valid copy of a block and must supply the data when needed. This is either the home node (if dirty bit is OFF) or the dirty node (if dirty bit is ON).|
|**Exclusive node**|A node that has a copy in its cache in an exclusive state (either dirty or clean-exclusive, as the case may be).|

> **PYQ (2024 Q25):** The node that currently holds the valid copy of a block and must supply the data when needed is called the **(c) Owner node.**

> **PYQ (2024 Q24):** The directory entry for a block contains **(b) the list of caches that currently contain a copy of the block** (via the presence bit vector).

#### When a Node Incurs a Cache Miss

When node ii incurs a cache miss (read or write), it first **communicates with the directory entry for the block** — it does NOT broadcast on the network or snoop the bus. The directory entry is located at the home node for the block. Node ii's communication assist looks up the address of the memory block to determine if the home is local or remote. If remote, a network transaction is sent to the home node. The directory is looked up, and the assist at the home node treats the miss as follows.

> **PYQ (2025 Q26, 2022 Q28, 2023 Q6, 2024 Q—, 2018 Q11, 2019 Q—):** When a node incurs a cache miss, it first **(b) communicates with the directory entry for the block.** It does NOT broadcast, does not snoop, does not contact the owner directly first.

#### Read Miss: Operation at Home Node

**Case 1 — Dirty bit is OFF:** Main memory has a clean (valid) copy. The communication assist at the home node obtains the block from main memory, supplies it to the requestor ii in a reply network transaction, and turns presence[i]presence[i] ON.

**Case 2 — Dirty bit is ON:** Main memory is stale. The assist at the home node responds to the requestor with the **identity of the node whose presence bit is ON** (i.e., the dirty/owner node). The requestor then sends a request network transaction to that owner node. At the owner node, the cache changes its state to Shared and supplies the block to both the requesting node (which stores it in its cache in Shared state) and to main memory at the home node. The dirty bit is turned OFF, and presence[i]presence[i] is turned ON.

> **PYQ (2025 Q25):** On a read-miss at node-i, when the dirty-bit at the home node is OFF, the communication assist at node-j **(a) sends from its main memory the data to i and presence[i] is turned ON.**

> **PYQ (2025 Q52, 2019 Q30):** There is a read miss at node-i and the dirty bit is ON — **(a) the identity of the owner node is sent to the requestor.**

> **PYQ (2018 Q17):** If the dirty bit is ON, **(d) all of the above** — the home node sends the identity of the dirty node to i, the requestor sends a request to the owner node, and the owner supplies the block to the requestor.

> **PYQ (2018 Q18):** If the dirty bit is OFF, the communication assist at node-i **(a) obtains the block from main memory.**

#### Write Miss: Operation at Home Node

**Case 1 — Dirty bit is OFF:** Main memory has a clean copy. Invalidation request transactions must be sent to all nodes jj for which presence[j]presence[j] is ON. Assuming a strict request-response scenario, the home node supplies the block to the requesting node ii together with the presence bit vector. The directory entry is cleared, leaving only presence[i]presence[i] ON and the dirty bit ON. (If the request is an upgrade rather than a read-exclusive, an acknowledgment containing the bit vector is returned to the requestor instead of the data itself. The assist at the requestor sends invalidation requests to the required nodes and waits for invalidation acknowledgment transactions from those nodes, indicating that the write has completed with respect to them. Finally, the requestor places the block in its cache in dirty state.)

**Case 2 — Dirty bit is ON:** The block is first recalled from the dirty node (whose presence bit is ON), using network transactions with the home and the dirty node. That cache changes its state to Invalid, and then the block is supplied to the requesting processor, which places it in its cache in dirty state. The directory entry is cleared, leaving only presence[i]presence[i] ON and the dirty bit ON.

> **PYQ (2025 Q24):** There is a write-miss at processor-i and the dirty bit is ON. After processing, **(a) only presence[i] remains ON** — the dirty node's presence bit is cleared.

> **PYQ (2019 Q31):** There is a write-miss at node-i and the dirty bit is OFF. Then **(d) both (b) and (c)** — invalidation requests are sent to all nodes jj for which presence[j]presence[j] is ON, AND the requestor obtains the block from the home node and places it in its cache in dirty state.

> **PYQ (2022 Q26):** On a write-miss at node-i for a cache block that is not dirty, **(d) both (b) and (c)** — the home node sends the presence bit-vector to node-i, and node-i sends invalidation requests to all caches sharing that block.

> **PYQ (2022 Q24, 2024 Q26):** A cache read-miss occurs at node-i. The home node is a remote node. At the home node, the dirty bit for the block is ON. **(d) both (b) and (c)** — node-i sends a request to node-j, and if dirty, node-j sends to node-i the identity of the owner node.

> **PYQ (2022 Q25):** When a dirty node provides data to a requestor node on a read miss, the state of the block **(a) changes to "shared"** at both the dirty node and the requestor.
