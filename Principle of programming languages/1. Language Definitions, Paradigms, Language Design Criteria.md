**1. What is a Programming Language?**

A **programming language** is a formal notation for describing computation that is simultaneously **machine-readable** and **human-readable**. Its primary role is to act as a bridge between two fundamentally different domains:

- **Real-World Problems**: Ambiguous, informal, described in natural language and domain concepts (business rules, physical simulations, data workflows).
- **Digital World**: Precise, deterministic, binary instructions executed by hardware processors.

To fulfil this dual role, every language design must satisfy two rigid requirements:

**Requirement 1: Machine Readability**

The syntax and structure of a language must be simple and precise enough for an automated translator (compiler or interpreter) to parse and execute efficiently:

1. **Unambiguous & Finite**: There must exist a deterministic translation algorithm that terminates with exactly one valid interpretation.
2. **Bounded Complexity**: The time/space complexity of translation cannot be arbitrarily high; translating a program must never cost more than executing it.
3. **Context-Free Structure**: Practical languages rely primarily on **context-free grammars (CFGs)** so parsing constructs does not depend on arbitrary surrounding context.

**Requirement 2: Human Readability**

Programs are written, maintained, and audited by human software engineers. Human readability requires:

1. **Abstracting the Hardware**: Shielding programmers from raw registers, memory buses, and machine bit-patterns.
2. **Supporting Localization**: Grouping related data and routines together so bugs can be identified and isolated easily.
3. **Enabling Collaboration**: Allowing software teams to communicate across large codebases.



**2. The Role & Hierarchy of Abstraction**

**Abstraction** is a notation or technique for expressing complex ideas in a concise form that hides unnecessary lower-level details, setting the human mind free to focus on higher-level problem solving. 

Abstractions in programming fall into **two general types** across **three structural levels**:

|Abstraction Level|Data Abstraction|Control Abstraction|
|---|---|---|
|**Basic** (Atomic / Local)|Hides bit representation of atomic values (ints, floats).|Combines machine instructions into single statements / syntactic sugar.|
|**Structured** (Intermediate)|Groups data elements into composite structures (arrays, records/structs).|Governs execution flow via structured blocks (loops, ifs, subroutines/procedures).|
|**Unit** (Large-Scale)|Bundles data + operations into reusable units (ADTs, classes, packages/modules).|Groups related subroutines into standalone modules/libraries or concurrent threads/tasks.|

**A. Data Abstraction Tiers**

- **Basic Data Abstractions**: Hide internal bit encodings of primitive values. For instance, a 32-bit signed integer `int x = 25;` hides 2's-complement binary representation (`00000000 00000000 00000000 00011001`), while `float` hides IEEE-754 single-precision format. These values are **atomic** because programmers cannot directly alter individual internal component bits.
- **Structured Data Abstractions**: Collect component data elements into a single composite entity. They are non-atomic (programmers can access individual elements). Examples include **arrays**, **records/structs**, and **files**.
- **Unit Data Abstractions**: Bundle a collection of data together with the subroutines that operate on that data, enforcing **encapsulation** and **information hiding**. Examples include **Abstract Data Types (ADTs)**, Java **classes/packages**, Python **modules**, and Rust **crates**.

**B. Control Abstraction Tiers**

- **Basic Control Abstractions**: Combine low-level machine instructions into readable expressions or assignment statements. A key concept here is **syntactic sugar**:language constructs provided solely to make code easier to write without adding new expressive power (e.g., `x += 10` instead of `x = x + 10`, or Python list comprehensions).
- **Structured Control Statements**: Replace low-level assembly branch/jump instructions (`JMP`, `BRz`) with structured control flow: selection (`if-else`, `switch`) and iteration (`while`, `for`).
- **Unit Control Abstractions**: Standalone collections of subroutines that provide logically related services across a program or system (e.g., C's `<math.h>`, Java's `java.util`, or concurrent primitives like Ada `tasks` and Java `threads`).



**3. Hardware Evolution & The Von Neumann Roadblock**

**The Von Neumann Architecture**

Traditional hardware follows the **Von Neumann model**, consisting of a central processing unit (CPU) that sequentially fetches instructions and executes them against a shared memory store. Imperative programming directly abstracts this hardware model:

1. **Variables** represent physical memory locations.
2. **Assignment statements** mutate values stored in those memory locations.
3. **Control flow** proceeds sequentially instruction by instruction.

**The Dual Roadblocks**

Around 2005, computing hit two major roadblocks:

1. **Hardware Roadblock (Thermal Wall & Von Neumann Bottleneck)**: Clock speed growth saturated because densely packed single-core silicon generated excessive heat. Furthermore, throughput was limited by the **Von Neumann Bottleneck** (the sequential transfer channel between CPU and memory). Hardware shifted toward multi-core CPUs and specialized accelerators (GPUs).
2. **Language Roadblock (Mutable Shared State)**: Sequential, variable-mutating imperative code maps poorly onto multi-core systems. Shared mutable state leads to non-deterministic race conditions and concurrency bugs that are notoriously difficult to debug.

**The Non-Von Neumann Solution**

Programming languages do not need to mimic single-processor sequential hardware. Alternative models of computation such as **Functional Programming** (rooted in Alonzo Church's **Lambda Calculus**) and **Logic Programming** (rooted in First-Order Predicate Logic) treat computation as mathematical function evaluation or logical inference, completely decoupling language abstractions from sequential hardware.


**4. The Four Major Computational Paradigms**

A **programming paradigm** is a fundamental style or model of building and structuring computation.

| Paradigm               | Underlying Computational Model                     | State & Variable Concept               |
| ---------------------- | -------------------------------------------------- | -------------------------------------- |
| **1. Imperative**      | Von Neumann architecture (sequential instructions) | Mutable variables bound to memory [24] |
| **2. Object-Oriented** | Interacting objects passing messages               | Encapsulated state inside objects      |
| **3. Functional**      | Lambda Calculus / Mathematical functions           | Immutable bindings (no side-effects)   |
| **4. Logic**           | First-order predicate calculus & formal logic      | Symbolic relations / Horn clauses      |

Euclid GCD algorithm written in 4 distinct paradigms:

```c
/* 1. IMPERATIVE (C) - Focuses on sequential state mutation */
int gcd(int u, int v) {
    while (v != 0) {
        int t = v;
        v = u % v;
        u = t;
    }
    return u;
}
```

```cpp
// 2. OBJECT-ORIENTED (Java) - State and operation bundled inside a class
public class IntNumber {
    private int value;
    public int gcd(int v) {
        int z = value, y = v;
        while (y != 0) {
            int t = y;
            y = z % y;
            z = t;
        }
        return z;
    }
}
```

```lisp
;; 3. FUNCTIONAL (LISP/Scheme) - Expression transformation via recursion
(define (gcd u v)
  (if (= v 0)
      u
      (gcd v (modulo u v))))
```

```prolog
% 4. LOGIC (Prolog) - Declarative logical predicate equations
gcd(U, V, U) :- V =:= 0.
gcd(U, V, X) :- 
    V =\= 0, 
    Y is U mod V, 
    gcd(V, Y, X).
```


**5. Language Design Criteria & Design Trade-offs**

**What Makes a Language "Successful"?**

A programming language is deemed successful if it meets any of three conditions:

1. **Achieves its original design goals**: It delivers what its designers set out to build: efficiency, readability, portability, or whatever the stated aim was. (e.g., FORTRAN achieved fast target code execution; COBOL achieved English-like business readability)
2. **Attains widespread commercial adoption:** It becomes the working language of a real application area, and stays there long enough to accumulate code. (e.g., C, C++, Java, Python).
3. **Serves as a structural model** for future languages (e.g., Algol60 introduced block structures and recursion; Smalltalk pioneered object-oriented message passing)

**Regularity (The Principle of Least Astonishment)**

**Regularity** measures how well a language integrates its features. Greater regularity means fewer unusual restrictions on constructs, fewer strange interactions between them, and fewer surprises in the way features behave. A regular language breaks down into three distinct sub-principles:

```
                                  REGULARITY
                   (Principle of Least Astonishment)
                                     |
         +---------------------------+---------------------------+
         |                           |                           |
  1. GENERALITY             2. ORTHOGONALITY             3. UNIFORMITY
  Combines related          Constructs combine           Similar things look
  constructs; avoids        without context              & behave similarly;
  special cases.             restrictions.             dissimilar look different.
```

1. **Generality**: Avoids special cases by combining closely related features into a single, general construct.
2. **Orthogonality**: Language constructs can be combined in any meaningful way without context-dependent restrictions.
3. **Uniformity**: Similar concepts look and behave similarly, while dissimilar concepts look different.

Why do regularities happen?

-> Compatibility: The C++ class semicolon is an unavoidable byproduct of deviating from C
as little as possible.

-> Implementation simplicity: C and Pascal restrict functions because both opt for a simple stack-based runtime environment.

-> Efficiency: Java's split between primitive and reference types exists so that simple data gets fast access.

-> Over-correction: Algol68 largely met its generality and orthogonality goals, and many designers believe that made it needlessly obscure and complex.



**Security**

**Security** maximizes the number of programming errors that can be automatically caught by the compiler before execution. Security introduced explicit type declarations and static type checking.

-> A language designed with security in mind both discourages programming errors and allows errors to be discovered and reported.

-> Security concerns introduced types, type checking and variable declarations into programming languages

-> Ex- Pointers are restricted in Pascal, barely restricted in C, eliminated in Java at the cost of a more complicated runtime

Price of security:

-> An exclusive focus compromises expressiveness and conciseness
-> It forces the programmer to specify as much as possible explicitly
-> Lisp and Python programmers find static checking makes generic utilities hard to write
-> Industrial, commercial and defence work often needs the extra guarantees anyway

**Efficiency: Execution vs. Programmer**

Efficiency is two-fold:

- **Execution Efficiency**: Translator generates fast, compact machine code (static typing, fixed-size arrays, manual memory management).
- **Programmer Efficiency**: Expressiveness and ease of writing code (dynamic typing, garbage collection, high-level abstractions).
- **Software Engineering Reality**: Software engineers spend **~90% of their time on maintenance and debugging**, and only **~10% on writing original code**. Therefore, **maintainability** is the single most critical economic measure of programming language efficiency.
