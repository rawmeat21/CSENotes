**1. Language Design Criteria & Design Trade-offs**

**What Makes a Language "Successful"?**

A programming language is deemed successful if it meets any of three conditions:

1. **Achieves its original design goals**: It delivers what its designers set out to build: efficiency, readability, portability, or whatever the stated aim was. (e.g., FORTRAN achieved fast target code execution; COBOL achieved English-like business readability)
2. **Attains widespread commercial adoption:** It becomes the working language of a real application area, and stays there long enough to accumulate code. (e.g., C, C++, Java, Python).
3. **Serves as a structural model** for future languages (e.g., Algol60 introduced block structures and recursion; Smalltalk pioneered object-oriented message passing)


**2. Efficiency of programming languages**

Language designers usually think of the efficiency of the target code first. That is, they strive for a language design that allows a translator to generate efficient executable code.

**Example 1: Static typing**

For static types, because the data types of these two variables are known at compile time, the compiler can guarantee that only integer and string operations will be performed on them. Thus, the runtime system need not pause to check the types of these values before executing the operations.

For dynamic typed languages, the absence of a type specification at compile time forces the runtime system to check the type of a Python variable’s value before executing any operations on it. This causes execution to proceed more slowly than it would if the language were statically typed.

-> Another view of efficiency is programmer efficiency, which describes how quickly and easily can a person read and write a program in a particular language.

-> A programmer’s efficiency is greatly affected by a language’s expressiveness: for example, how easy is it to express complex processes and structures, or how easily can the design in the programmer’s head be mapped to actual program code. This is related to the language’s abstraction mechanisms. 

-> The structured control statements of Algol and its successors are wonderful examples of this kind of expressiveness. 


**An unreliable program is expensive because of these reasons:**

• Modifications are needed to isolate the erroneous behaviour
• Then more to remove it, plus extra testing time
• Then time to correct the effects the error already caused
• In the worst case, development and coding time is wasted entirely
• This is a resource-consumption issue in software engineering


**3. Regularity (The Principle of Least Astonishment)**

**Regularity** measures how well a language integrates its features. Greater regularity means fewer unusual restrictions on constructs, fewer strange interactions between them, and fewer surprises in the way features behave. A regular language breaks down into three distinct sub-principles:

```
                                  REGULARITY
                   (Principle of Least Astonishment)
                                     |
         +---------------------------+---------------------------+
         |                           |                           |
  1. GENERALITY             2. ORTHOGONALITY             3. UNIFORMITY
  Combines related          Constructs combine           Similar things look
  constructs; avoids        without context              & behave similarly;
  special cases.             restrictions.             dissimilar look different.
```

1. **Generality**: A language achieves generality by avoiding special cases by combining closely related features into a single, general construct.

Examples:

-> **Procedures and functions** 

---> Function and procedure definitions can be nested in other function and procedure definitions in Pascal. They can also be passed as parameters to other functions and procedures. However, Pascal functions and procedures cannot be assigned to variables or stored in data structures. 

---> In C, one can create pointers to functions to treat them as data, but one cannot nest function definitions. 

---> Python and most functional languages, such as Scheme and Haskell, have a completely general way of treating functions (nested functions definitions and functions as first-class data objects).

-> **Operators**

---> In C, two structures or arrays cannot be directly compared using the equality operator but must be compared element by element. Thus, the equality operator lacks generality. This restriction has been removed in Smalltalk, Ada, Python, and (partially) in C++ and Java.

---> Haskell permits overloading of existing operators and allow new operators to be created by the user. In such languages, operators can be viewed as having achieved
complete generality.

-> **Constants**

---> In Pascal, the values assigned to constants may not be computed by expressions, while in Modula-2, these computing expressions may not include function calls. Ada, however, has a completely general constant declaration facility.


2. **Orthogonality**: An orthogonal design allows language constructs to be combined in any meaningful way, with no unexpected restrictions or behavior arising as a result of the interaction of the constructs, or the context of use.

-> **Function return types** 
---> In Pascal, functions can return only scalar or pointer types as values. 

---> In C and C++, values of all data types, except array types, can be returned from a function. 

---> In Ada, Python, and most functional languages, this lack of orthogonality is removed.

-> **Placement of variable declarations** 
---> In C, local variables can only be defined at the beginning of a block (compound statement).

---> C++ variable definitions can occur at any point inside a block (before any uses).

-> **Primitive and reference types** 

-> In Java, values of scalar types (char, int, float, and so forth) are not objects, but all other values are objects. Scalar types are called _primitive types_, whereas object types are called _reference types_. 

-> Primitive types use value semantics, meaning that a value is copied during assignment. 

-> Reference types use reference semantics, meaning that assignment produces two
references to the same object. 

-> Also, in Java, collections of objects are treated differently from collections of primitive types. Among Java’s collections, only arrays can contain primitive values. Primitive values
must be placed in special wrapper objects before insertion into other types of collections. 

-> In Smalltalk and Python, by contrast, all values are objects and all types are reference types. Thus, these languages use reference semantics only, and collections of objects are treated in an orthogonal manner.

3. **Uniformity**: refers to a design in which similar things look similar and have similar meanings and, inversely, in which different things look different.

-> **Extra semicolon**
--->  In C++, a semicolon is necessary after a class definition, but forbidden after a function definition. 

-> **Using assignment to return a value**
---> In Pascal, return statements in functions look like assignments to variables. This is a case where different things should look different, but instead look confusingly alike. Most other languages use a dedicated return statement for returning values from functions.

![](../assets/Pasted%20image%2020261121203757.png)


Why do irregularities happen?

-> Compatibility: The C++ class semicolon is an unavoidable byproduct of deviating from C
as little as possible.

-> Implementation simplicity: C and Pascal restrict functions because both opt for a simple stack-based runtime environment.

-> Efficiency: Java's split between primitive and reference types exists so that simple data gets fast access.

-> Over-correction: Algol68 largely met its generality and orthogonality goals, and many designers believe that made it needlessly obscure and complex.


**4. Security**

Reliability of a programming language can be seriously affected if restrictions are not imposed on certain features.

**Security** maximizes the number of programming errors that can be automatically caught by the compiler before execution. Security introduced explicit type declarations and static type checking.

-> A language designed with security in mind both discourages programming errors and allows errors to be discovered and reported.

-> Security concerns introduced types, type checking and variable declarations into programming languages

-> Ex- Pointers are restricted in Pascal, barely restricted in C, eliminated in Java at the cost of a more complicated runtime


**Price of security:**
-> An exclusive focus compromises expressiveness and conciseness.
-> It forces the programmer to specify as much as possible explicitly
-> Lisp and Python programmers find static checking makes generic utilities hard to write and make it difficult to program complex operations
-> Industrial, commercial and defence work often needs the extra guarantees anyway

**5. Extensibility**

-> An extensible language allows the user to add features to it. Most languages are extensible at least to some degree.

-> For example, almost all languages allow the programmer to define new data types and new operations (functions or procedures). Some languages allow the programmer to include these new resources in a larger program unit, such as a package or module. The new data types and operations have the same syntax and behavior as the built-in ones.

-> Very few languages allow the programmer to add new syntax and semantics to the language itself. 

-> One example is LISP. Lisp programmers add new functions, classes, data types, and packages to the base language.

-> They can also extend Lisp’s syntax and semantics via a macro facility. A macro specifies the syntax of a piece of code that expands to other, standard Lisp code when the interpreter or compiler encounters the first piece of code in a program. The expanded code may then be evaluated according to new semantic rules.

->  For example, Common Lisp includes a quite general do loop for iteration but no simple while loop. Lisp programmer solve this by simply defining a macro that tells the interpreter what to do when it encounters a while loop in a program.
